A Claude Code plugin that creates and edits https://github.com/j-specman/specman[Specman]
specifications (`.nsd`, SUCs) and implements or synchronizes code based on them.

== Why

Specman `.nsd` files are a textual DSL defined by an ANTLR grammar
(`reference/SpecmanModel_V002.g4`). Since 2.0.0 the plugin no longer ships a parser or editing
scripts: the skills tell Claude to edit the `.nsd` text directly against the grammar and a complete
worked example (`reference/specman-reference-v1.4-model-v2.nsd`), and the Specman jar
(`--sanitize`) validates and normalizes the result. What remains as code is only what Claude cannot
do reliably by hand: running the jar and reconciling step-number references in source code.

The sanitizer checks grammar conformity and a few invariants (duplicate step IDs, unresolvable
steplinks); it renumbers steps and regenerates `plain=` fields. It does *not* validate
`source`/`target` move links or `markups=` offsets — the skills contain hard rules for these (see
<<limits>>).

== Installation

[source]
----
/plugin marketplace add zorak1103/specman-plugin
/plugin install specman@specman-plugin
----

== Prerequisites

* Java (to run the Specman sanitizer jar)
* The environment variable `SPECMAN_JAR`, set to the full path of
  `specman-*-jar-with-dependencies.jar` (Specman *1.4.0 or newer*). The jar itself is not part of
  this plugin (~50-70 MB) — see `VENDORING.md`.

[source,bash]
----
export SPECMAN_JAR="/path/to/specman-1.4.0-jar-with-dependencies.jar"
----

On Windows, set it as a user or system variable and restart Claude Code. The skills `plan` and
`edit` check the variable in "Step 0", before touching anything, and abort with a clear message if
it is missing or invalid; the same check by hand:

[source,bash]
----
node scripts/resolve-jar.mjs --json
----

== Skills

[cols="1,4"]
|===
| Skill | Purpose

| `plan`       | Interview-guided creation of a new SUC or sub-SUC file from the template
| `edit`       | Targeted change to an existing `.nsd` file, edited directly and validated with the jar
| `implement`  | Implement code from a specification or, for large scope, create a phase plan
| `sync-refs`  | Reconcile `SUC-XXX Step N (ID: xxx)` references in code (Java/TypeScript) with the current spec state; also recognizes the legacy German keyword `Schritt`
|===

All four can be invoked by the model and are available via `/specman:<name>`.

The `.docx` migration (`migrate` skill) of 1.x was removed in 2.0.0.

== `.wrk` working copies (Specman autoload)

If an `.nsd` file is open in Specman (with autoload enabled), Specman creates a working copy
`<file>.nsd.wrk` and reads only that. The skills edit and read the `.wrk` when it exists — otherwise
saving in Specman would overwrite your change with the old state. `sync-refs` also prefers the
`.wrk`.

== Change tracking

When `changeModeEnabled` is on in the diagram settings, `edit` marks whole new elements as
`change=(added, <changeset>)` and removed ones as `change=(removed, <changeset>)`. Anything else
(text changes inside existing elements, step moves, `markups=` offsets) is refused and handed back
to the user — do it in Specman itself.

[[limits]]
== What the plugin does not do

* *Step moves with change tracking* (`source`/`target` pairs) — neither Specman nor the sanitizer
  validates the `sourceStep=` link; a faulty reference crashes the GUI on load.
* *Character-offset `markups=`, steplinks, `backup=`* — offsets are not validated; the skill never
  writes them by hand and does not edit text that carries steplink markups without asking.
* *Rendering or syntax checking of PlantUML* — the source text can be edited, Specman renders it.
* *`.docx` migration* — removed in 2.0.0.
* *Migration from V001 (legacy JSON)* — open and save once in Specman 1.3.0+.
* *Consistency check of running-text cross-references between SUC files*.

== sanitize and idempotence

`sanitize.mjs` rewrites the file *in place* — never run it on a file you have no backup of. For
specs with a leading empty `<div>` in intro/outro text blocks (the template!), the sanitizer
reports `Plain text fields refreshed` on every run; after a `SANITIZED`, `sanitize.mjs` performs a
second run and reports `stable: true` if the file stays byte-identical — that is the idempotence
statement, not the counter.

== Configuration

`.claude/specman.local.md` (not committed):

[source,yaml]
----
---
specDir: <path to the project-specific SUC folder>
author: <abbreviated name for the document history, e.g. "M. Mustermann">
---
----

`author` is asked for the first time a history row is written (first name abbreviated to an initial)
and is remembered here (`scripts/specman-config.mjs`).

== Document history

`plan` fills the template row `0.1 | Initiale Erstellung` (author, today's date, follow-up `Review`);
`edit` appends *one* row per editing pass with a suggested, confirmed version number (wording-only
change → `x.(y+1)`, added/removed steps or changed flow → `(x+1).1`). The plugin never writes review
rows. In change mode the new row is marked like any added element
(`change=(added, <changeset>)` on its cells, as in the reference file).

== Development

[source,bash]
----
node --test "test/**/*.test.mjs"
----

`scripts/` holds `sanitize.mjs`, `resolve-jar.mjs`, `specman-config.mjs`, `sync-refs.mjs` and the
two helpers in `scripts/lib/`. For the origin and updating of the vendored files in `reference/`,
see `VENDORING.md`.
